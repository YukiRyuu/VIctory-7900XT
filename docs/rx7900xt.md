# Notes from an RX 7900 XT (2026-11-25 to 2026-11-26)

One PC: Radeon RX 7900 XT 20 GB (driver 32.0.32015.7029), Ryzen 7 7800X3D,
31 GB RAM, Windows 11 26300, Series X profile, diagnostics build. Started with
`scripts\play.ps1 -RX7900XT` (the settings below; until 2026-11-26 a `.cmd`
with the same settings). Frame rates are medians of the
log's frame lines in the world (prologue and first mission).

## Where it stands

| Run | Settings | fps in the world | Note |
|---|---|---|---|
| 1 | `play.ps1` | 12.7-13.4 | pipelines made while playing, ran out of commit |
| 2 | + `victory warm`, `CARD_BUFFERS_MIN_MB=1`, `CARD_BUFFERS_MB=1536` | 15.9 (peak 26) | out of commit at a cutscene skip |
| 3 | + `ROOT_WINDOW_MB=12`, `WINDOW_KB=1024` | 18.2 (peak 27) | 33 min, then out of commit |
| 4 | page file raised to 32-88 GB | 18.1 | allocator swaps measured (below) |
| 7 | + `TEXTURE_STAGE_MS=80`, `INPLACE=1` | 18.7 | preparing 45 -> 37 ms a frame |

## Memory (commit, not RAM, is the limit)

- The process commits 35-40 GB during play, more in bursts: skipping a
  cutscene took it from 32.0 to 39.4 GB in 40 s. With 31 GB of RAM the
  commit limit (RAM + page file) must leave room: the page file on D: was
  raised to 32 GB initial, 88 GB most (Windows caps one page file at three
  times the RAM), which ended the out-of-commit crashes.
- `VICTORY_WINDOW_KB=1024` with `VICTORY_ROOT_WINDOW_MB=12`: windows of title
  memory outside buffers from 6.9 GB to 1.3 GB at the same point.
- About 21 GB of the process is write-combined memory, 3-5 GB of it in RAM.
  Not this layer's upload buffers (6.3 GB made in a whole run) nor its host
  copies (write-back). Replacing host lists' command allocators every 128
  resets (`VICTORY_ALLOCATOR_RESETS=128`) released 2 MB in 12,288 swaps: it
  is not the allocators either, or the driver keeps what they held. Off by
  default; the owner of that memory is not found yet.
- The title's 6.2 GB page pool is reserved, not committed (`SEC_RESERVE`):
  only what is mapped counts.

## Faults found

- **Device removed in the intro (page fault).** A root view has no size and
  was given its 4 MiB cell of title memory only; a shader read 0xbfd000 bytes
  into a window and past it, into freed memory (DRED). Fixed: a root view's
  window reaches the title memory committed around it, up to
  `VICTORY_ROOT_WINDOW_MB` (shadow.rs `root_window`).
- **Out of commit** ("no host list for a state prelude", 0x8007000E): above.
- **Device reset 0x887A0007** ("some other application"): another program
  reset the driver; not the layer.

## Tree flicker

Not the indirect budget (`indirect records ran empty`: 0 in every run) and not
the two indirect paths (`INDIRECT_WINDOW=0 INDIRECT_BATCH=0`: still flickers,
half the frame rate). Suspected, not tested: copies that have no
per-submission snapshot (`send.rs` takes one for copies in the card's memory
only). With `VICTORY_RELAY` two frames of submissions are prepared ahead, and
a window or a small buffer copy in the PC's memory is refreshed for a later
submission before an earlier one has read it, so its draws see the next
frame's per-frame data. Test: a run without `RELAY` and `LATE_WAIT`. A capture
key is there for it: with `VICTORY_CAPTURE`, F11 saves the next 8 frames.

## The unified-memory direction

Most of a frame is the cost of two memories: in a 53 ms frame the write watch
10.8 ms, refreshes 11.5, copy-back 16.1, waits on the trackers' locks 26 ms of
all threads. The card is about 67 % busy.

What this PC's driver can do (a probe, and `VICTORY_INPLACE_PROBE=1`):

- GPU upload heaps (Resizable BAR): yes; the CPU wrote 64 MiB into VRAM at
  20.5 GB/s. Not usable for direct sends: with two frames in flight an earlier
  submission would read a later one's bytes (the reason `send.rs` exists).
- Opening the title's memory as a heap (`OpenExistingHeapFromAddress`, `...1`):
  yes. The GPU sees the CPU's writes with no call between, and the CPU reads
  what the GPU wrote: the console's behaviour, with no copy.
- A reserved section is refused as a heap; a committed one is taken, and a
  buffer placed over a view's pages works while the view is made read-only or
  unmapped.

`VICTORY_INPLACE=1` placed only 123-135 windows (about 230 MB): 5,000 more lie
in view memory. The title's views of physical pages are 13.2 GB in 107,962
views, almost all of one 64 KiB page, over three reserved sections (6,236,
710 and 185 MB). Tile mappings into an opened heap remove the device, so the
way in is: make the sections committed, and give each title page its place in
the section when the title first maps it, in the order of its addresses (as
`map_whole` does for the 185 MB heap), so that runs of title addresses are runs
of the section and one placed buffer covers each.

Per-copy bus traffic (copies in the card's memory, one frame): 38 MB up, 60 MB
fetched; a 174 MB buffer mostly sent up, several 3-11 MB buffers only fetched
(written by shaders, read back): the second kind are the next candidates for
in place.

## Tried and not kept: the title's GPU memory on the card (ForwardVI)

ForwardVI's `VICTORY_CARD_MEMORY=1` (the title's 2.2 GB write-combined
reservation made of the card's memory through Resizable BAR, its buffers and
windows used in place) was ported and run here. It works (no faults) but is
slower on this PC, and characters' faces render black, as in ForwardVI's runs:

| Run | | fps median | p10 |
|---|---|---|---|
| 7 | without | 19.4 | 8.7 |
| 8 | card memory | 15.5 | 5.9 |
| 9 | + copy-backs that do not read the card | 12.7 | 1.3 |

The processor reads the card's memory at about 30 MB/s. In run 8 it read
8.5 GB of it, 7.8 GB in texture copy-backs and 0.6 GB in texture refreshes;
run 9 cut that to 152 MB and was no faster. Texture time went from 0.8 to 13
ms a frame and GPU time from 2.8 to 16.6. The work is kept on the local branch
`forwardvi-port` (with ForwardVI's driver shader-cache trim, which let 6.4 GB
of the driver's mapped cache files go from memory).
